# Guardians and admissions — founder checklist

Use [SMS Production](https://sms-web-shoaibhasann.vercel.app/login) after the release owner confirms this office revision is Ready. Record the revision/date, role, school, device, expected/actual result and a redacted issue reference. These boxes are founder acceptance and remain separate from engineering tests.

Use privately supplied dedicated QA accounts: School Admin, Principal, a second Admin session, Teacher, Guardian/Student, Finance/Reception and another school's administrator. Use synthetic admission numbers and pupils. Keep passwords, tokens, QR/setup secrets, live codes, mobile numbers and private pupil records out of screenshots/public issues. Do not modify a shared founder/demo account or real-school data to exercise a negative case.

## Guardians

- [ ] OW-01 — As School Admin, open People → Guardians. Verify the actual selected school, guardian names/codes, registered-mobile labels and expected linked children/admission numbers. Old browser-local demo records must not appear.
- [ ] OW-02 — Search by a linked child's name and admission number, then by a controlled QA guardian code/mobile. Clearing search restores the source. A missing term shows a clear empty result, not a fake zero for the entire school.
- [ ] OW-03 — With a fixture of more than 24 guardians, use Next/Previous and search for a record beyond the first page. The rendered page stays bounded while the search covers the complete loaded directory. Refresh retains the saved source, not unsaved browser records.
- [ ] OW-04 — Check active, inactive and unlinked school-profile fixtures. The badge must describe the school profile only. A school registered-mobile field must not be presented as proof of native phone, email or MFA verification. Retained withdrawn-child links remain identifiable without restoring a revoked link. With a current academic year set, each linked child shows one of three states: active (enrolled this year), withdrawn (withdrawn this year) or not enrolled this year (an active pupil with no current-year placement).
- [ ] OW-05 — Admin's Manage guardian access link opens the existing Guardian invitations workflow. The directory itself has no inline account creation, contact edit, revoke or re-invite action. Check those existing verified workflows using their own checklist.
- [ ] OW-06 — Sign in as Principal. The same authorized school directory is readable; no Admin-only Manage guardian access action appears. Another school's Guardian records remain absent.

## Real admissions

- [ ] OW-07 — As Admin, open People → Admissions. Select the authorized current year/class/section. Enter a fresh synthetic admission number, first name, optional last name, a synthetic date of birth and a synthetic 10-digit registered mobile, then Admit student. The saved class register shows one pupil; hard refresh still shows that pupil in the same section. A future date of birth or a malformed mobile is rejected with no pupil saved. Sign up a fresh synthetic account and complete /activate → Student with that admission number, DOB and mobile: activation succeeds, also when the mobile is typed as +91 98765 43210, 919876543210 or 09876543210 (sign up a fresh account for each format). A wrong mobile shows only "Student verification failed".
- [ ] OW-08 — Repeat with a Principal and a different synthetic admission number/section. Admissions must reuse the actual roster; fake enquiry stages, available seats and application Approve/Reject controls are absent. Students still provides the existing placement/withdrawal/history workflow. Edit details on a roster pupil corrects the name and adds or changes the DOB and registered mobile (only School Admin and Principal see Students); Audit Logs shows Student details updated without the values. A pupil whose saved mobile or DOB is in an older format can still have a name typo fixed; only the fields actually changed are checked and logged. A pupil admitted without DOB/mobile can activate once they are added. Withdraw is refused with "Resolve this pupil's pending attendance corrections before withdrawing." while a correction for that pupil awaits review; approve or reject it first. Withdraw a disposable synthetic pupil (the dialog says a School Admin or Principal can reinstate during the current academic year), then use Reinstate in Withdrawal history with a reason: the same pupil and admission number return to the register, a staged next-year promotion is restored, and Audit Logs shows both the withdrawal and the reinstatement. A withdrawal from a previous session cannot be reinstated and shows no Reinstate button.
- [ ] OW-08a — Year-end bulk promotion: after adding a later academic year, open Students for a synthetic section and use Promote this section. Only later, non-overlapping years are offered; all active pupils start ticked; untick one, choose the destination class/section, enter a reason and review the count before Stage promotion. The notice reports how many were staged and how many already had a staged placement (those keep it; revise them with Change placement). The unticked pupil stays unplaced in Academics → Activate next academic year. A pending attendance correction on one ticked pupil stages nobody and names that pupil's admission number. Placement history and Audit Logs show one promotion entry per pupil with the same reason; retrying after a dropped response does not add entries.
- [ ] OW-09 — Try the same admission number again in that school, then the same number in a different letter case or with extra spaces (for example `adm-7` after `ADM-7`). Each attempt, and a student CSV that repeats a number in another case, must fail as a duplicate with no extra pupil/enrollment. Guardian CSV rows match the pupil whatever the admission-number case. A separate authorized school may use its own same admission number without exposing the first school's pupil.
- [ ] OW-10 — In two authorized QA sessions, submit the same school/admission number concurrently. Exactly one official student/enrollment should remain. During a normal save, repeated clicking must not start another submission.
- [ ] OW-11 — Use a controlled QA network-interruption case. An unknown single-save result keeps its original draft and disables another admission/CSV action until Reload roster succeeds. Reconcile whether the pupil already exists before starting another admission; do not invent a new admission number to bypass uncertainty.
- [ ] OW-12 — Open student CSV import. Verify the template (admission_number, first_name, last_name, date_of_birth as YYYY-MM-DD or spreadsheet DD-MM-YYYY, shown as YYYY-MM-DD in the preview, registered_mobile; an older three-column file still imports), preview, class/section and owner before importing valid synthetic rows. A row with an invalid date (not a real YYYY-MM-DD or DD-MM-YYYY date, before 1900-01-01 or after today in IST) or an invalid mobile is rejected in the preview with its row number. Reload the register and reconcile every imported pupil. Invalid/duplicate input must not be reported as a successful batch. Recent CSV imports then lists the batch with the importing account, IST time and pupil count (batches saved before import history show Unknown · Before import history), and Audit Logs shows a Student admitted event for each new pupil, including single admissions.
- [ ] OW-13 — For an uncertain CSV result, Retry same import retains the same reviewed rows/request identity; the school/context stays locked. A confirmed duplicate can be corrected. Changing accounts or navigating away during a file read/save must discard obsolete UI results rather than importing into the next owner/context.

## Access, history and UX

- [ ] OW-14 — Try direct Guardians (/modules/parents) and Admissions URLs as Teacher, Student, Guardian, Finance and Reception. These office screens must deny unsupported roles. Existing family-own reads and intentional office raw-read capabilities are separate; do not infer a new role grant from a menu or mock test.
- [ ] OW-15 — Ask the engineer to run the current API boundary checks: raw client INSERT into students/enrollments is denied even for Admin, while governed Admin/Principal admit/import/placement and legitimate assigned-class Teacher registration still work. No Finance orphan should be created through the released boundary. Do not paste service credentials into the browser to test this.
- [ ] OW-16 — With disposable fixtures, remove an office role while that same account remains signed in, then refresh the directory. Private rows/actions disappear or access fails explicitly; an allowed own-family subset must not be mislabeled as the full school directory. Switching school/account during a pending read must not display the old school's late response.
- [ ] OW-17 — Recheck the existing QA siblings, attendance, fees/receipts, Guardian child links and notification read counts before/after this phase. An admission must not rewrite another pupil's history or reset another Guardian's read state. Record any differences privately for reconciliation.
- [ ] OW-18 — Test laptop and narrow-phone layouts in both themes, keyboard focus, long names, loading/error/empty states, bounded guardian lists and button progress. Account/context changes during a pending save must not show an old success in the new account. Founder signs off independently after recording actual results.

This release does not activate email/SMS/FCM delivery, add an enquiry CRM/seat-management system, complete all remaining web modules or integrate an attendance device. Physical notification/hardware acceptance remains a separate controlled pilot.
