# Optional Guardian arrival and exit alerts

7 November 2026 · Hosted migration/local workflow verified · Main release pending

Arrival and exit alerts are independent opt-in choices for each Guardian/child relationship. Both default OFF. A canonical Absent mark continues to create the existing eligible Guardian absence alert regardless of these choices. A missing gate scan does not automatically declare a child Absent. This release concerns the school inbox; no SMS or real FCM dispatch is enabled.

## Behavior and authority

- Only current verified linked Guardians with attendance access can read or change their own choices. Each link has an immutable preference UUID and version. Revoke/re-invite and recovered-login ownership changes start a new OFF epoch; an old open form cannot restore consent or old gate alerts.
- An accepted, non-future current-day IN can create one arrival alert per child/Guardian/day. An accepted OUT needs a preceding accepted same-day IN before it can create one exit alert. OUT without IN, held events and historical/future events create no gate alert. Re-entry, different event IDs, exact retries and simultaneous delivery cannot duplicate a daily alert.
- Creation and inbox/count/read actions recheck current link, owner, role, school and the selected option. Turning an option OFF hides its retained alerts; ON may show retained alerts from the same consent epoch with their existing read state. Previously processed scans missed while OFF are not backfilled. A newly received buffered same-day scan uses its actual event time and a Delayed label after five minutes.
- Arrival/exit preferences do not mute absent attendance, published results or leave decisions. Revoked links cannot receive new gate or absence alerts or read the revoked child's old alerts; independently authorized siblings remain available.
- New notifications live in a separate private table. Legacy three-kind family inbox/count/read APIs, absence logic and native push routines remain unchanged. Four explicit `_v2` inbox/count/read APIs add `gate_arrival`/`gate_exit`, actual `occurred_at` and `delayed` metadata; old clients keep their original payloads and counts.
- Web Notifications and updated native app source expose per-child preferences and the five-kind inbox. Web requests pin the verified native owner/JWT. Native requests use the Auth provider's immutable-session client. Stale actions are aborted; unknown/conflicting saves require refresh/reconciliation before another change.

## Operator and founder handoff

Use [the focused founder checklist](../../public/qa/gate-alerts-checklist.md). Preference RPCs are `get_my_gate_alert_preferences` and `set_my_gate_alert_preferences`; the setter requires the current preference UUID, version and both choices. The existing authenticated gate endpoint is unchanged. The new inbox/count/single-read/bulk-read methods are `get_family_notification_inbox_v2`, `get_family_notification_unread_count_v2`, `mark_family_notification_read_v2` and `mark_all_family_notifications_read_v2`.

Testing must use fresh isolated pupils/links/preferences. Preserve existing child links, old unread timestamps, attendance and finance. Send synthetic events through the actual managed Edge endpoint, not a simulated successful notification. Retain actual event IDs and exact retry receipts privately; never put login/device credentials in the public checklist.

Real hardware, vendor adapters, native binary distribution, OS notification permission, Firebase delivery and funded SMS remain separate acceptance. The original gate backend boundary is in [GATE-ATTENDANCE-QA](GATE-ATTENDANCE-QA.md). No real-school, physical presence or phone-delivery certification is made by synthetic inbox QA.

Arrival/exit source selection intentionally suppresses even slightly future timestamps, although the attendance core tolerates a bounded clock offset. An OUT received before its qualifying IN is not later backfilled. Current API eligibility is authoritative; already rendered/offline screens require refresh to reflect revocation.
