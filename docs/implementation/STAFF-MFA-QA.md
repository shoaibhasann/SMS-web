# Staff authenticator MFA

7 November 2026 · Engineering evidence is separate from founder acceptance

Founder checklist: [MFA-01–MFA-15](https://kids-corner-erp-frontend.vercel.app/qa/staff-mfa-checklist.md). Stable app: [SMS Production](https://kids-corner-erp-frontend.vercel.app/login).

## Implemented scope

Native Supabase TOTP supplies optional authenticator setup, verification, named backup factors, subsequent sign-in challenges and factor removal. No factor secrets are stored in application tables, logs, local storage or public QA artifacts. An account with any verified TOTP honors MFA even when school policy is OFF, including a pure family account. School-required MFA covers all staff roles and all roles of a mixed staff/family account. A true global platform administrator always requires MFA.

School Admins can read rollout counts and save an audited policy with a reason after current native AAL2 verification. Principals can read it. The policy is OFF by default and cannot be enabled while any distinct active staff account lacks verified TOTP. Enabled schools guard new staff-role grants and reactivation. Two Admin saves use a revision conflict; actor-bound exact retry receipts preserve an uncertain outcome without another policy change. History exposes the latest ten sanitized events, not internal payloads or recovery data.

The bootstrap RPC returns only the current verified active account's security status. The standalone `/mfa` route can complete setup before a zero-role account accepts an invitation. Web server access, module routes, account settings and the shared shell check that status before protected profile/role reads. MFA work uses a captured, verified, nonpersistent Auth client; verification refreshes the current primary session without copying isolated tokens. Own-password changes keep fresh password proof separate from the current AAL2 mutation session.

The separate native app checks the same bootstrap before family records load. It adds existing-factor challenge, wrong-code retry, background cancellation and sign-out. Enrollment opens the stable website without transferring tokens; native enrollment itself is not implemented. Family access/child scope is rechecked after successful verification.

## Recovery and rollout

Before enabling a real school, enroll every active staff account, verify a backup authenticator for administrators, agree the authorized operator and identity-verification process, and rehearse lost-device recovery using a disposable account. A password reset proves first-factor recovery; it does not clear the authenticator or satisfy the school-data gate. This phase provides no automated factor reset or recovery-code product. A trusted operator can manage native Auth after independently verifying identity; do not disable a whole school's policy to recover one user.

No paid SMS channel, explicit recovery/invitation email or Firebase send is part of this QA. Supabase may emit managed security emails for MFA/password operations; absence of SMTP markers in a sampled log window is not proof of no email delivery. Provider notification settings/delivery remain a separate operational check.

Guardian mobile enrollment/change still uses its separate fresh first-factor proof session. That session cannot bypass MFA for an enrolled Guardian; a combined temporary-session TOTP/contact-change UI is not part of this staff slice. Paid phone sending remains OFF. Complete that reauthentication UX and real carrier checks before activating phone changes for MFA-enrolled family accounts. A password-recovery session likewise never clears a factor or grants school data by itself.
