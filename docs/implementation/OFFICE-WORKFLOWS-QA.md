## Office workflows

`/modules/parents` now renders `ParentDirectoryWorkspace` for School Admin and Principal instead of the browser-local demo. School selection comes from current manager access. Reads bind the verified owner and pin its JWT to every request. Before and after collecting the directory, the loader rechecks that owner's current same-school Admin/Principal role or legitimate global Super Admin scope, plus access to the exact active school. Losing office authority on the same Auth UID therefore fails explicitly instead of displaying an allowed family subset as the complete school directory.

The loader reads parents, only their linked school profiles, their child links and only those same-school pupils. Exact-count ordered pages account for lower server row caps; IDs are chunked in groups of 100. Missing counts, duplicate identities/link pairs, cross-school rows and incomplete profile/child mapping fail closed. This is a complete current read, not a transaction snapshot. The UI renders 24 guardian cards per page while searching the full loaded source, including guardian code, registered mobile and child/admission identifiers. It retains pupils who have withdrawn and never recreates a removed relationship.

Badges mean **Active school profile**, **Inactive school profile** or **No linked profile**; they do not certify native Auth status, email verification or MFA. **School registered mobile** is a school record, not proof of current carrier ownership. Profile email/phone and native Auth users are not queried to invent verified contact claims. Admin gets a link to the existing Guardian invitations/access workflow. Principal sees the directory read-only, with no new inline edit, account creation or child-link bypass.

`/modules/admissions` reuses `StudentRosterWorkspace view="admissions"`, its governed `admit_roster_student` RPC, reviewed student CSV import and actual saved class register. There is one admission implementation. A confirmed admission creates the student and active enrollment atomically for the authorized current year/class/section. The screen has no fabricated application approval/rejection, enquiry stages, available-seat count or separate CRM record. Placement, withdrawal and their histories remain in the existing Students workspace rather than being duplicated in Admissions.

Single admission and CSV RPCs pin the captured owner. Account/context changes abort UI continuations and discard obsolete drafts/previews; a late result cannot be adopted into a replacement login. An unknown single-admission result freezes its draft and CSV action until a successful roster reload reconciles the saved source. A known validation/duplicate/access error remains distinct. School-specific admission uniqueness protects retries and competing requests. Unknown CSV outcomes retain the reviewed payload and request ID, hold the school context and offer **Retry same import** rather than manufacturing a fresh batch.

## Roles and database boundary

Only School Admin/Principal are routed to these new office screens. Reception's Parents/Admissions navigation grants are removed; direct URLs do not bypass the role gate. Existing Accountant/Reception school-scoped raw directory reads are intentional database capabilities and are not claimed to be denied by this UI change. A Guardian may still read its own parent/child rows through the family data boundary; a Teacher does not receive bulk Parent access.

Hosted migration `20261107072011_harden_legacy_function_access.sql` has source SHA-256 `47c992680836fd9cac12c66f4a22a48245e07cd009dd346d6acafe851bc36a19` and SQL MD5 `06d58fea78bf0b177ebe0974474fbed1`. It pins the two ordinary legacy trigger/audit search paths, removes anonymous execution of two legacy privileged helpers, and moves Teacher contact changes behind a checked private implementation with an INVOKER public wrapper. That implementation checks the current native actor, one coherent active Teacher profile, current Teacher role, active school and MFA boundary. It updates only that Teacher's school contact field; it does not verify or change a native Auth phone number.

The preflight also exposed raw client `students` INSERT: Finance could create an orphan student row while its enrollment INSERT was rejected. The revised migration removes raw client INSERT into **both `students` and `enrollments`, including for Admin**. Reviewed postgres-owned Admin/Principal admission/import/placement functions and the legitimate assigned-class Teacher registration function remain the authorized creators. No claim is made that every Teacher is forbidden from every student-creation capability; assignment-scoped registration is preserved and tested separately.

The first whole migration attempt failed with ownership error 42501 when trying to alter five platform-owned generated `LANGUAGE internal` timetable constructors. Its transaction rolled back. The revised source removes only those unsupported metadata alterations, verifies their native immutable constructor contract, and leaves their ownership/implementation/index dependencies intact. No ownership escalation or platform bypass is used; the revised migration applied successfully.

Advisors are **not clean**. Current readback has zero anonymous SECURITY DEFINER notices, five unchanged platform-owned internal-constructor search-path warnings, five intentional authenticated SECURITY DEFINER warnings and one disabled leaked-password-protection warning. Private RLS/no-policy INFO entries are expected deny-all implementation tables. These remaining warnings/settings need operational review; this phase does not activate a paid setting or claim managed-service recovery.

## Scope still open

Admissions is the governed act of admitting/enrolling a pupil, not an enquiry/application CRM or a seat-capacity system. Reception admission permissions, a new permission editor and new staff provisioning remain separate decisions. Parent contact/link mutations continue through the existing verified workflows. Events, Admin Notifications, School Profile, Documents, Reports and operations modules retain their separate backlog/demo boundaries.

The user confirms that no attendance device exists yet. [The device pilot brief](../product/ATTENDANCE-DEVICE-PILOT.md) records the decisions and real-hardware tests required before choosing an adapter. Notification delivery should activate the already built native push backend through approved provider/device checks; this phase adds no gateway, sends or simulated hardware success.
